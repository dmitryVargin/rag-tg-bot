# Отчет: Архитектура и стек технологий для RAG-бота QuantumForge

**Дата:** 24.05.2024  
**Автор:** AI Architect  
**Цель:** Выбор оптимального стека для корпоративной базы знаний с учетом требований безопасности (SOC 2) и специфики данных (18к+ технических документов).

---

Это задание требует роли **System Architect / Lead AI Engineer**. Я буду готовить этот отчет для CTO и Security Officer (CISO) компании QuantumForge.

Учитывая профиль компании (Финляндия/Эстония, клиенты вроде ABB, SOC 2 аудит), ключевыми факторами принятия решений будут:
* **Безопасность данных** (GDPR, NDA)
* **Точность ответов** (техническая документация)
* **Интеграция в AWS**

Ниже представлен отчет по исследованию инфраструктуры и инструментов.

---

## 1. Сравнение LLM-моделей (Generation Layer)

Мы выбираем «мозги» системы. Учитывая географию компании (EU), использование YandexGPT не рассматривается из-за рисков GDPR и санкционных политик. Сравниваем лидеров рынка и Open Source.

| Характеристика | Облачные (OpenAI GPT-4o) | Локальные (Llama 3 70B / Mixtral 8x22B) |
| :--- | :--- | :--- |
| **Качество ответов** | Эталонное. Отлично следует сложным инструкциям, хорошо работает с кодом и контекстом. | Высокое. Llama 3 70B приближается к GPT-4, но требует тщательного промптинга. Модели 8B/7B для сложного RAG не подойдут. |
| **Скорость работы** | Зависит от нагрузки на API. В среднем 20-50 токенов/сек. | Стабильная, зависит от нашего железа. Можно оптимизировать через vLLM / TGI. |
| **Приватность** | Средний риск. Данные покидают периметр (даже при Zero Retention Policy). Требует подписание DPA (Data Processing Addendum). | Максимальная. Данные не покидают контур AWS EKS компании. Полный контроль. |
| **Стоимость** | Pay-as-you-go. Дорого при большом объеме токенов, но нет CAPEX затрат. | Высокий CAPEX (аренда GPU инстансов 24/7). Дешевле только при очень высокой нагрузке. |
| **Сложность внедрения** | Низкая (API Key). | Высокая (Нужен MLOps, балансировка, мониторинг падения подов). |

**Вывод по разделу:** Для MVP и старта лучше подходит облако (Enterprise подписка), но для промышленного использования с сенситивными данными (Digital Twin спецификации) стратегически верно иметь возможность переключения на локальную модель.

## 2. Сравнение моделей эмбеддингов (Retrieval Layer)

Модель, которая превращает текст в векторы. Это критический компонент для качества поиска.

| Характеристика | Облачные (OpenAI text-embedding-3) | Локальные (Sentence-Transformers / E5-large / BGE-m3) |
| :--- | :--- | :--- |
| **Качество поиска** | Хорошее универсальное, но "черный ящик". Работает с 8k токенов контекста. | Отличное. Модели типа BGE-M3 или multilingual-e5 часто превосходят OpenAI в бенчмарках (MTEB), особенно на специфичных доменах. |
| **Скорость индексации** | Зависит от API rate limits. Платно за каждый документ. | Очень быстрая при наличии GPU. Бесплатно (open source). |
| **Безопасность** | Текст документов отправляется во внешнее облако. | Полная безопасность. Векторизация происходит внутри контура. |

**Вывод по разделу:** Рекомендую **Локальные модели** (Hugging Face).
* Это дешевле (индексация 18k файлов через API стоит денег, а при переиндексации — снова).
* Это безопаснее (текст документов не улетает в API).
* Модель `multilingual-e5-large` отлично работает с миксом языков (En, Fi, Ee).

## 3. Векторные базы данных: ChromaDB vs FAISS

Нам нужно хранить векторы и метаданные (кто автор, какая версия, права доступа).

| Характеристика | FAISS (Facebook AI Similarity Search) | ChromaDB |
| :--- | :--- | :--- |
| **Суть** | Библиотека для быстрого поиска ближайших соседей. Это "движок", а не база данных. | Полноценная векторная база данных (Vector Store) с API. |
| **Метаданные** | Нет из коробки. Нужно писать свой слой mapping'а (ID вектора -> Текст/Метаданные). | Встроено. Позволяет делать запросы типа: `where={"source": "confluence"}`. |
| **Сложность внедрения** | Высокая для продуктовой среды. Нужно самим решать вопросы персистентности (сохранения на диск) и CRUD операций. | Низкая. Работает как сервер, легко поднимается в Docker/K8s. |
| **Скорость** | Экстремально быстрая (миллисекунды). | Высокая (использует HNSW индексы под капотом). Достаточна для наших объемов. |
| **Стоимость** | CPU/RAM (Open Source). | CPU/RAM (Open Source). |

**Вывод по разделу:** Для RAG-бота, где важны фильтры по правам доступа (разработчик не должен видеть зарплатные ведомости, если они попадут в индекс), **ChromaDB** выигрывает безоговочно. FAISS — это low-level решение, которое усложнит поддержку.

## 4. Конфигурация сервера (Hardware)

Расчет для объема: ~25 000 документов (чанкинг по 500 токенов ≈ 100-150 тыс. векторов).

### Вариант А: Только векторная БД + Бэкенд (LLM в облаке)
* **CPU:** 4 vCPU
* **RAM:** 16 GB (ChromaDB хранит индексы в памяти для скорости)
* **GPU:** Не требуется (или слабый T4 для эмбеддинга, если хотим ускорить индексацию).
* **Disk:** 100 GB SSD (NVMe).

### Вариант Б: Полный Self-Hosted (Llama 3 70B + БД)
* **CPU:** 16+ vCPU
* **RAM:** 64 GB+ system RAM
* **GPU:** 2x NVIDIA A100 (80GB) или 4x A10G (для квантованной модели). Llama-3-70B в fp16 требует ~140GB VRAM.
* **Disk:** 500 GB SSD.

## 5. Итоговые рекомендации: 3 Варианта архитектуры

### Вариант 1: "Максимальная безопасность" (On-Premise Fortress)
* **Стек:** Llama 3 (Self-hosted) + Local Embeddings + ChromaDB.
* **Плюсы:** Данные никогда не покидают AWS компании. Полное соответствие SOC 2 без оговорок.
* **Минусы:** Огромная стоимость железа (~$3-5k/мес за GPU инстансы). Сложная поддержка.
* **Вердикт:** Избыточно дорого для старта.

### Вариант 2: "Быстрый старт" (Cloud Native)
* **Стек:** OpenAI API (GPT-4) + OpenAI Embeddings + Pinecone/Chroma (Managed).
* **Плюсы:** Запуск за 2 дня. Оплата только за использование.
* **Минусы:** Риски безопасности. Передача данных третьей стороне. Не подходит для строгих NDA.

### Вариант 3: "Сбалансированный Enterprise" (Рекомендованный) ⭐
* **Стек:**
    * **LLM:** Azure OpenAI Service (развернутый в регионе Europe West). Microsoft предоставляет Enterprise-гарантии, что данные не используются для дообучения моделей (в отличие от обычного OpenAI).
    * **Embeddings:** Локальные (Hugging Face) на CPU/малом GPU внутри нашего контура.
    * **Vector DB:** ChromaDB, развернутая в нашем кластере EKS.
* **Аргументация:**
    1. Azure OpenAI закрывает вопрос качества генерации и юридической безопасности (SLA, Compliance).
    2. Локальные эмбеддинги + Chroma гарантируют, что полный текст базы знаний индексируется у нас, а в облако улетает только маленький кусочек контекста в момент вопроса пользователя.
    3. Экономия на GPU (не нужно хостить LLM 24/7).

## Финальный выбор инструментария

Мы будем использовать **ChromaDB** в связке с локальной моделью эмбеддингов `intfloat/multilingual-e5-large` (так как у нас смешанный язык и техдокументация) и **Azure OpenAI (GPT-4)** для генерации ответов.

**Почему ChromaDB?**
* Легкая интеграция в текущий стек Python/AWS.
* Поддержка метаданных критична для реализации разделения прав доступа (менеджеры/разработчики).
* Open Source (нет vendor lock-in).
